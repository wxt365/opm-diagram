## 3. 术语约定

| 术语 | 本文含义 |
| --- | --- |
| OPM | 对象过程方法论；当指 ISO 19450:2024 时使用该缩写 |
| OPL | Object-Process Language；在 ISO 19450:2024 中指表达 OPD 模型的英语自然语言子集及其文本模态 |
| OPD | 对象过程图，OPL 模型的图形表达 |
| OPT | 对象过程文本，是中文 OPL 草案对文本模态的命名；不是 ISO 19450:2024 使用的正式术语 |
| 文本模态 | 对 ISO 配置档指 OPL Paragraph/Sentence；对中文草案配置档指 OPT |
| 图文等价 | 同一模型的 OPD 与对应文本模态具有一致语义 |
| OPD process tree | ISO 配置档中以 SD 为唯一根、通过过程细化关系连接各 OPD 的有向树 |
| OPD object forest | ISO 所称 OPD object tree 的产品级表达；由多个可细化对象分别作为根形成的对象上下文森林，不与 OPD process tree 合并为一棵树 |
| System map | 显式展示 OPD process tree、各 OPD 所含元素及其关联的模型导航视图 |
| Model view | 按明确条件选择并呈现模型中既有事物、过程、关系或 Model Fact 的 OPD 上下文；不等同于细化子 OPD |
| 视口缩放 | 仅改变画布显示比例的放大、缩小操作，不改变模型语义 |
| 语义内缩放/外缩放 | OPM in-zooming/out-zooming 上下文细化与抽象机制，会改变 OPD 表达的模型上下文和对应文本 |
| 结点 | 事物、对象、过程、值域、值等可命名模型元素的统称 |
| 关系 | 连接结点并表达静态、动态或一般性语义的模型元素 |
| 配置档 | 对特定标准或语言扩展所允许元素、语法、语义和校验规则的集合 |
| 模型基线 | 经校验后由用户生成、可追溯且不可被原地覆盖的本地模型版本 |

产品公共界面应使用“文本视图”或“图文同步”。进入具体配置档后，ISO 配置档使用“OPL”，中文草案配置档使用“OPT”，不能在两个配置档之间混用术语。

## 4. 背景与问题

现有通用绘图工具可以绘制类似 OPD 的图形，但通常缺少以下能力：

- 不理解 OPL 模型元素及关系的形式语义；
- 无法持续保证 OPD 与对应 OPL/OPT 文本模态图文等价；
- 无法管理 OPD 上下文结构、命名空间、可见性和跨图引用；
- 无法按照任务架构、功能架构、产品架构组织工程模型；
- 无法针对主体、客体、手段、资源、环境、信息等角色做完整性检查；
- 无法区分 ISO 19450:2024 与中文 OPL 草案扩展；
- 无法形成可评审、可追溯、可发布的模型基线。

产品需要从“语义模型”出发生成图和文本，而不是分别保存互不关联的图形与文字。

OPM 建模采用“一个模型、多张相互关联的 OPD”。根 OPD 建立系统功能、边界和总体上下文，后续 OPD 通过对象或过程的标准细化机制逐层表达结构、行为、状态和约束。多张 OPD 不是多个独立模型，也不是对一张大图的机械切片，而是同一语义模型在不同上下文和细节层级下的表达。

在 ISO 配置档中，过程细化 OPD 组成以 SD 为唯一根的 OPD process tree，对象细化 OPD 组成可包含多个对象根的 OPD object forest。按条件汇集既有模型事实形成的 model view 独立于这两类细化结构管理。三者共享同一语义事实源，但具有不同的上下文来源和导航语义。

## 5. 产品目标

### 5.1 总体目标

建设一个单用户、单设备运行的 OPM 建模工具，使建模者能够通过本地界面编辑 OPD，并由系统按当前配置档实时生成语义等价的文本模态（ISO OPL 或中文草案 OPT），同时提供标准配置档、语义校验、层级建模、架构方法引导、本地版本基线和模型交换能力。

### 5.2 业务目标

- 降低 OPM/OPL 建模工具的使用门槛；
- 让建模者通过图形和自然语言形式检查模型，并可导出材料供外部评审；
- 通过自动校验减少错误关系、语义歧义和模型不一致；
- 支持复杂模型的分层组织、复用、本地版本和基线管理；
- 将 OPM 模型沉淀为可演化、可版本化、可追溯和可复用的业务语义资产；
- 为后续需求管理、架构设计、仿真分析或本体发布提供结构化模型源。

### 5.3 成功标准

- 用户能够在单台设备上创建、编辑、保存、关闭并重新打开本地模型；
- 每次有效 OPD 变更都能生成与当前模型和配置档一致的 OPL/OPT 文本；
- 非法关系不会被静默接受，并能定位到具体元素和规则；
- 模型可以明确声明标准配置档，并产生对应的兼容性检查结果；
- 用户能够从 OPD 和对应文本模态两种表达检查同一模型；
- 一个模型能够包含多张相互关联的 OPD，跨图出现的同一元素保持统一身份和一致语义；
- 已发布基线可追溯、可比较，且不会被后续草稿覆盖。

## 6. 单机版使用边界

首期按照单用户单机版设计：

- 单次运行只面向一名本地使用者，不建立用户、组织、租户或角色模型；
- 不提供登录、身份认证、角色授权、项目成员管理和权限审计；
- 模型、配置档、版本和导出物默认保存在本地设备；
- 核心建模、校验、图文生成、版本和导出能力不依赖云端服务；
- 可以使用本地浏览器作为交互界面，但服务默认只面向本机，不构成在线 SaaS；
- 外部评审通过导出文件完成，不在首期提供站内评论、审批和协同工作流。

## 7. 典型使用场景

### 7.1 从空白 OPD 建模

建模者创建项目和根 OPD，从元素面板拖入结点、建立关系、编辑属性。系统按配置档实时更新 OPL/OPT 文本，并在发生语义错误时给出定位提示。

### 7.2 分层细化复杂模型

建模者从根 OPD 开始，选择过程创建 process tree 中的细化 OPD，或选择对象创建 object forest 中的细化 OPD，通过对应导航结构在概要与细节上下文之间切换。系统保证跨图同一元素的身份、属性和关系事实一致，并允许按明确条件建立不改变事实身份的 model view。

### 7.3 使用架构方法开展系统设计

建模者按任务架构、功能架构、产品架构组织模型，使用 `6×1` 检查和功能信息模式检查发现角色或信息链路遗漏，并记录架构分析与决策。

### 7.4 图文联合检查与导出

用户同时查看 OPD 及其对应 OPL/OPT 文本，通过元素与语句联动检查模型，并导出图文报告供外部评审。

### 7.5 标准兼容检查

建模者选择 ISO 19450:2024 或中文 OPL 草案配置档。系统按所选配置档限制可用元素并执行校验；当模型使用配置档外扩展时，系统明确标记并生成兼容性报告。

### 7.6 生成本地模型基线

通过阻断性校验的模型版本可生成只读本地基线，保留配置档、模型内容、OPL/OPT 文本、校验结果、基线说明和生成时间，可供后续设计或其他系统消费。

## 8. 产品范围

### 8.1 首期必须包含

- 单用户单机运行，可使用本地浏览器界面；
- 项目、模型和 OPD 上下文结构管理；
- 一个模型包含多张相互关联 OPD 的分层建模，以及 process tree、object forest 和 model view 的分类导航；
- OPD 图形编辑；
- 结点、关系和属性编辑；
- OPD 变更按配置档实时生成只读 OPL/OPT 文本；
- 图文定位联动；
- 语法、语义和模型完整性校验；
- 标准配置档声明与兼容性检查；
- 自动保存、版本快照、本地基线、备份和恢复；
- 基本导入、导出和可打印输出；
- 任务/功能/产品三层架构分类及方法检查。

### 8.2 后续阶段候选能力

- 直接编辑 OPL/OPT 文本并反向更新 OPD；
- 多人同时编辑同一 OPD；
- 用户、组织、角色、权限和租户管理；
- 登录认证、云端同步、链接分享和在线评审；
- 仿真执行和过程动画；
- AI 辅助建模、语义补全和模型审查；
- 与需求管理、PLM、ALM、本体平台的深度集成；
- 企业级模型仓库、分支合并和跨项目依赖管理；
- 三维模型或 STEP 文件关联。

### 8.3 明确非目标

- 首期不替代通用 CAD、BPMN、UML 或 SysML 工具；
- 首期不提供任意自由图形绘制能力；
- 首期不承诺完整系统仿真或形式化证明；
- 首期不支持用户自定义底层语言语义；
- 首期不将中文草案扩展自动视为 ISO 19450:2024 标准元素；
- 首期不以 OPL/OPT 文本作为独立事实源；语义模型是 OPD 和文本模态的共同事实源；
- 首期不建立账号体系、角色权限、项目成员、评论审批或多人协同能力；
- 首期不要求依赖远程服务才能完成核心建模工作；
- 本需求阶段不冻结前后端技术栈、数据库、部署架构和 API。

## 9. 核心产品原则

### 9.1 单一语义事实源

OPD 图形布局和 OPL/OPT 文本不是两套独立模型。系统必须保存统一的语义模型，并从该模型派生 OPD 表达和相应配置档的文本表达。

### 9.2 图文等价优先

只有成功提交到语义模型的有效编辑才进入正式 OPL/OPT 文本。编辑中的临时图形状态可以短暂存在，但必须明确显示为未提交或无效状态。

### 9.3 标准差异显式化

每个模型必须声明配置档。配置档外元素必须被阻止，或以明确的扩展标记保存，不能静默降级。

### 9.4 分层而不分裂

OPD 上下文结构用于控制复杂度。多张 OPD 共同表达一个模型；细化 OPD 必须记录被细化元素和父级上下文，model view 必须记录选择条件和事实来源。同一语义元素跨 OPD 出现时必须保持统一身份，不能复制成无关联副本。

### 9.5 方法引导而非强制模板

架构方法检查用于提示遗漏、风险和建议，不应把所有领域模型强制成同一种图形布局。

### 9.6 业务语义资产

OPM 模型不是一次性图纸。模型、OPD、元素、关系、文本模态、版本、校验结果和基线共同构成可演化的业务语义资产。OPM 基线可以作为下游本体定义的输入，但 OPM 模型不自动等同于本体；进入本体平台必须经过明确的映射、校验和受控发布。

## 10. 功能需求

优先级定义：`MUST` 为首期必需，`SHOULD` 为首期建议，`COULD` 为后续候选。

### 10.1 项目与模型管理

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-PROJ-001 | MUST | 用户能够创建、重命名、归档和恢复项目。 |
| FR-PROJ-002 | MUST | 项目至少包含名称、说明、默认配置档、本地存储位置和创建时间。 |
| FR-PROJ-003 | MUST | 一个项目能够包含一个或多个 OPM 模型。 |
| FR-PROJ-004 | MUST | 用户能够从空白模型或受控模板创建模型。 |
| FR-PROJ-005 | MUST | 模型创建时必须选择配置档，后续切换配置档前必须先执行影响检查。 |
| FR-PROJ-006 | SHOULD | 用户能够搜索本地项目、模型、OPD 和结点。 |
| FR-PROJ-007 | MUST | 一个 OPM 模型必须作为统一语义资产管理，并能够包含多张相互关联的 OPD。 |

### 10.2 OPD 上下文结构与导航

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-OPD-001 | MUST | ISO 配置档的每个模型必须有且只有一个 SD，并以该 SD 作为 OPD process tree 的唯一根；OPD object forest 中的对象根和 model view 不得被解释为第二个系统根。 |
| FR-OPD-002 | MUST | 用户能够针对允许细化的过程创建 OPD process tree 中的细化 OPD，并针对允许细化的对象创建 OPD object forest 中的细化 OPD。 |
| FR-OPD-003 | MUST | 系统必须按照配置档区分展示 OPD process tree、OPD object forest 和 model views，并支持展开、折叠、定位和上下文路径导航。 |
| FR-OPD-004 | MUST | OPD 必须承担模型上下文和图形容器职责；结点名称唯一范围和命名空间规则由配置档决定。 |
| FR-OPD-005 | MUST | 系统区分 OPD 拥有的结点与引用的结点，并采用可辨识的视觉表达。 |
| FR-OPD-006 | MUST | 删除或移动 OPD 前，系统必须分析其拥有结点、引用关系、细化关系和 model view 定义的影响。 |
| FR-OPD-007 | SHOULD | 用户能够在父级概要关系与子级详细关系之间导航。 |
| FR-OPD-008 | SHOULD | 系统能够提示同一上下文中不必要的重复元素或跨层细节泄漏。 |
| FR-OPD-009 | MUST | ISO 配置档的根 OPD 必须是 System Diagram（SD），并以 SD 为 OPD process tree 的根。 |
| FR-OPD-010 | MUST | 根 OPD 必须按照配置档表达系统功能、边界和总体上下文；ISO 配置档通过 SD 实现。 |

## 11. 标准兼容需求

### 11.1 配置档模型

首期定义两个面向模型的配置档和一个内部公共语义内核。配置档正式名称和版本标识在原子规则集完成后冻结：

| 类型 | 目的 | 状态 |
| --- | --- | --- |
| 内部公共语义内核 | 承载两配置档已确认无损或满足明确条件后可无损归一化的事实；不作为用户可选择配置档 | 内核边界草案已建立，待元模型验证 |
| ISO 19450:2024 配置档 | 按 ISO 的符号、元素、方法和 OPL 语法限制模型 | 条款规则组已建立，待原子规则实现和测试 |
| 中文 OPL 草案配置档 | 支持仓库内中文 OPL 草案定义及其扩展 | 能力矩阵已建立，随草案版本演进 |

### 11.2 ISO 19450:2024 符合性目标

ISO 19450:2024 第 5 章定义以下三类符合性：

| 符合性类型 | ISO 要求 | 产品需求 |
| --- | --- | --- |
| 部分（符号）符合 | 仅使用第 4 章符号及第 7 至 12 章元素，并遵循标准赋予的语义 | ISO 配置档的最低模型合法性门槛 |
| 完全符合 | 满足部分符合，并遵循第 6 章和第 14 章的 OPM 建模方法 | ISO 模型校验和生成基线的门槛 |
| 工具制造商符合 | 满足部分符合；引导用户达到完全符合；按 Annex A EBNF 支持 OPL | 本产品的目标符合性类型 |

工具制造商符合性必须拆分为可验证的三个子目标：

1. `ISO-SYMBOLIC`：符号、元素、链接、状态、基数和逻辑语义符合第 4、7 至 12 章；
2. `ISO-METHOD`：SD、功能价值、系统边界和上下文细化引导符合第 6、14 章；
3. `ISO-OPL`：自动生成的英文 OPL 符合 Annex A 的 EBNF 规则。

Annex A 明确说明其 EBNF 对概率、执行路径和复杂参与约束等表达并不完备。因此 `ISO-OPL` 不能只依赖 EBNF 解析器，还必须结合第 7 至 14 章的规范性语义规则和测试样例。

### 11.3 ISO 配置档专属约束

- OPM Thing 只能是 Object 或 Process；State 是 Object 的从属状态，不作为独立 Thing 类型；
- ISO 不显式规定 Process state；中文草案中的过程值域、值等表达不得直接进入 ISO 配置档；
- Object 和 Process 必须支持 Perseverance、Essence、Affiliation 三类通用属性及标准规定的默认值语义；
- Link 分为 Procedural Link 和 Structural Link，不能直接套用中文草案的静态、动态、一般性关系分类作为 ISO 类型体系；
- 每个 Process 必须通过 Transforming Link 连接至少一个 Object 或 Object State；同一抽象层级中，同一 Object/Object State 相对同一 Process 只能承担一个过程角色；
- Thing 名称在整个 OPM 模型范围内唯一；不能使用中文草案的 OPD 局部命名空间规则放宽 ISO 名称唯一性；
- System Diagram（SD）是 OPD process tree 的根，必须表达利益相关方、受益者、系统功能及必要的系统内外部 Thing；
- OPD process tree 必须是以 SD 为唯一根的有向树；OPD object tree 按对象细化来源形成多个树组成的 forest，两类结构必须分别维护；
- System map 必须能够展示 OPD process tree 中各 OPD 的元素内容，并提供 Thing 出现位置、OPD process tree 和 OPD object forest 的导航；
- 按条件汇集元素形成的 model view 必须复用既有 Model Fact，并带有对应 OPL Sentence；model view 不得伪装成没有被细化元素的子 OPD；
- 上下文管理必须支持状态显式/抑制、展开/折叠、内缩放/外缩放三对机制；
- Process 内缩放中的垂直布局具有时间偏序语义，布局变更可能改变执行语义，不能一律视为纯视觉属性；
- ISO 文本模态必须自动生成英文 OPL Paragraph/Sentence，并遵循 Annex A 的标识符、保留短语、句式和上下文管理语法；
- OPD Construct、OPL Sentence 和 Model Fact 之间必须保留可追溯对应关系。

### 11.4 中文草案配置档专属约束

- 允许按中文草案定义事物、对象、过程、值域、值、流及扩展关系；
- 允许按中文草案使用 OPD 命名空间、公开/保护/私有可见性和跨 OPD 引用；
- 文本模态使用中文 OPT 术语及中文草案规定的标准句式；
- 中文草案中的位置、权属、一般性关联、关联算子和完整布尔运算不得被标记为 ISO 标准元素；
- 中文草案允许但 ISO 未定义或定义方式不同的元素，必须带有明确的配置档来源和扩展标识。

### 11.5 跨配置档兼容规则

- 每个模型和基线必须绑定配置档及其版本；
- 配置档定义允许的结点、关系、符号、属性、修饰符、文本句式和校验规则；
- ISO 配置档不得默认启用仅存在于中文草案中的扩展；
- 中文草案扩展导入 ISO 配置档时，必须生成阻断或有损转换提示；
- 配置档转换必须同时检查元素类型、状态模型、关系分类、命名范围、上下文机制和文本语言，不能只替换图形符号；
- 配置档升级必须提供影响分析和迁移报告，不得静默改变既有模型语义；
- 模型符合性报告必须区分“部分符合”“完全符合”“不符合”“无法判断”；
- 产品级符合性报告单独汇总 `ISO-SYMBOLIC`、`ISO-METHOD` 和 `ISO-OPL` 证据，判断是否达到工具制造商符合性；
- 配置档转换报告必须区分“无损映射”“使用扩展”“有损映射”“无法映射”；
- “符合 ISO 19450:2024”的产品声明必须以逐条映射矩阵、自动化规则测试和代表性模型互操作测试为证据。

### 11.6 条款级规则组与待建立的原子规则

`docs/requirements/iso-19450-2024-conformance-matrix.md` 已按以下主题建立子条款规则组、配置档追踪和证据类型：

1. 术语和基础语义；
2. 图形符号；
3. 结点类型及属性；
4. 静态关系；
5. 动态/过程关系；
6. Object State 与中文草案值域、值和过程状态的表示差异；
7. SD、OPD process tree、OPD object tree 与中文草案 OPD 树的差异；
8. ISO 英文 OPL、Annex A EBNF 与中文 OPT 句法；
9. 过程控制与事件语义；
10. 名称唯一范围、跨图复用与中文草案命名空间机制；
11. 状态显式/抑制、展开/折叠、内缩放/外缩放；
12. 模型交换、标识和扩展机制。

### 11.7 配置档能力矩阵

元素、关系、修饰机制、上下文能力和跨配置档差异以 `docs/requirements/opm-profile-capability-matrix.md` 为需求基线。ISO 规则组以 `docs/requirements/iso-19450-2024-conformance-matrix.md` 为追踪基线，公共无损事实边界以 `docs/requirements/opm-common-semantic-core.md` 为基线。后续原子规则必须继续映射图形符号、OPL 句式和自动化测试，不得另建不一致的能力枚举。

## 12. 核心信息对象与状态

### 12.1 核心信息对象

| 对象 | 关键含义 |
| --- | --- |
| 项目 | 本地模型、配置、版本、基线和导出物的管理边界 |
| 模型 | 统一语义事实源及其 OPD 与配置档文本表达集合 |
| OPD | 特定上下文的图形表达；必须记录上下文类型和来源，是否承担命名空间职责由配置档决定 |
| OPD process tree | 以过程细化关系组织的 OPD 有向树；ISO 配置档以 SD 为唯一根 |
| OPD object forest | 以对象细化关系组织的多个对象上下文树的集合 |
| Model view | 按选择条件汇集既有元素和 Model Fact 的 OPD 上下文，记录条件、来源和对应文本模态 |
| System map | 展示 OPD process tree、各 OPD 内容和跨上下文出现位置的模型导航视图 |
| 结点 | 具有稳定身份、类型、名称、属性和所属 OPD 的模型元素 |
| 关系 | 具有稳定身份、类型、方向、端点和修饰的模型元素 |
| OPL/OPT 语句 | 从语义模型按配置档生成的文本表达，保留与 OPD Construct 和 Model Fact 的映射 |
| 配置档 | 标准版本、元素规则、语法和校验规则集合 |
| 校验问题 | 规则执行产生的错误、警告或建议 |
| 模型版本 | 某一时刻语义、布局、配置档和校验结果的快照 |
| 模型基线 | 通过阻断性校验后由用户生成的只读本地模型版本 |
| 操作记录 | 本地动作、对象、结果和时间信息，不包含用户身份或权限信息 |

### 12.2 模型生命周期

```text
草稿 -> 校验中 -> 校验通过 -> 本地模型基线
  ^        |          |              |
  |        v          v              v
  +------校验失败----继续修改    基于基线创建新草稿
```

规则：

- 草稿可编辑；
- 校验通过的版本仍可继续修改，但修改后必须重新校验；
- 用户主动执行“生成基线”后才形成只读模型基线；
- 本地模型基线不可原地修改，只允许归档或基于基线创建新草稿；
- 配置档变化、导入覆盖或模型迁移均必须产生新版本。

## 14. 验收标准

### 14.1 核心主路径

1. 用户创建项目和 OPM 模型，选择配置档并创建根 OPD。
2. 用户在根 OPD 中建立系统功能、边界和总体上下文。
3. 用户针对过程创建 OPD process tree 中的细化 OPD，并针对对象创建 OPD object forest 中的细化 OPD。
4. 用户通过分类导航和 System map 在 process tree、object forest 及相关上下文之间定位；跨图同一元素保持相同稳定标识和一致语义。
5. 用户执行画布视口缩放时模型语义不变；执行配置档定义的内缩放、外缩放、展开、折叠、状态显式或抑制时，对应模型上下文和文本同步变化。
6. 每张 OPD，包括 SD、细化 OPD 和 model view，都实时生成对应 OPL Paragraph 或 OPT 章节，模型级文本能够按上下文结构汇总。
7. 用户选中图形元素时定位对应语句，反向选择语句也能定位图形元素。
8. 用户制造非法连接，系统阻止提交或产生阻断错误，并准确定位问题。
9. 用户完成校验并生成本地模型基线。
10. 重新打开基线后，完整 OPD 集、OPL/OPT 文本、配置档和校验结果保持一致且只读。
11. 用户备份项目，在新的本地目录恢复后，模型、版本和基线内容保持一致。

### 14.2 标准配置档验收

- 同一测试模型分别在 ISO 配置档和中文草案配置档中校验时，允许元素和扩展提示符合各自规则；
- ISO 配置档能够分别输出 `ISO-SYMBOLIC`、`ISO-METHOD` 和 `ISO-OPL` 三类检查结果，并汇总工具制造商符合性结论；
- ISO OPL 测试集覆盖 Annex A EBNF；对 Annex A 明确未覆盖的概率、执行路径和复杂参与约束，使用对应规范性章节规则验证；
- ISO 配置档能够阻止独立值域/值结点、Process state、OPD 局部重名等不符合 ISO 元模型的内容；
- ISO SD、单根 OPD process tree、多根 OPD object forest 和 System map 能够通过代表性模型验证；
- 状态显式/抑制、展开/折叠、内缩放/外缩放能够通过代表性模型验证，且测试能够证明画布视口缩放不会产生语义变更；
- 对声明支持的 model view，测试必须证明其选择条件、事实来源、稳定身份和对应 OPL Sentence 可追溯；
- 中文草案扩展进入 ISO 配置档时不会被静默接受；
- 配置档切换前能够列出不兼容元素和可能的有损转换；
- 兼容性报告能够追溯到具体元素、标准条款映射和规则版本；
- 配置档能力报告能够证明每个 `MUST` 能力已有实现和测试证据，并明确列出尚未实现的 `SHOULD`；
- 元素面板、关系菜单和导入器不能创建能力矩阵中标记为 `FORBIDDEN` 或未列出的类型；
- 在逐条符合性矩阵、规则实现和测试证据完成前，产品不得显示“已符合 ISO 19450:2024”的最终结论。

### 14.3 图文一致性验收

- 标准关系测试集中，每一种支持的关系均能生成预期 OPL/OPT 文本；
- 结点改名、关系改向、属性修改和删除后，受影响 OPL/OPT 文本同步变化；
- 跨 OPD 引用不会生成重复身份或矛盾语句；
- 每张 OPD 的文本段只表达该 OPD 当前上下文中显示的模型事实，模型级文本汇总不丢失 OPD 层级；
- 任意已发布基线中的每条正式 OPL/OPT 语句均能追溯到一个或多个模型元素；
- 存在无法生成配置档合法文本的正式模型元素时，模型不得发布。

### 14.4 业务语义资产验收

- 模型基线包含 SD、完整 OPD process tree、OPD object forest、全部已定义的 model views、跨图稳定标识、完整文本模态、配置档和校验结果；
- 两个模型版本之间能够按稳定标识比较新增、修改、删除和移动上下文的元素；
- 结构化业务语义资产包导出后能够在新的本地目录完整恢复模型；
- 未执行本体映射和发布时，资产包必须标记为 OPM 语义源，不得标记为已发布本体；
- 面向本体平台的发布包能够列出已映射元素、未映射元素、源基线和校验结论。

### 14.5 工程验收门槛

进入实现前必须补齐并评审：

- 顶层技术架构和模块详细设计；
- 元模型与标准符合性矩阵；
- 页面信息架构、状态、字段和组件交互设计；
- API 与持久化契约；
- 原型验收基线；
- 前端 handoff；
- 开发执行包和测试策略。

## 15. 验证方式

需求阶段采用以下验证方式：

1. 对照三份参考资料和配置档能力矩阵检查术语、OPD、OPL/OPT 文本模态、元素、关系、修饰机制、OPD 上下文结构、可见性、过程语义和架构方法是否被需求覆盖；
2. 检查所有功能需求是否具有唯一编号、优先级和可验证描述；
3. 检查首期范围、后续能力与非目标是否明确分离；
4. 检查 ISO 19450:2024 兼容声明是否被证据门槛约束；
5. 检查模型状态、阻断条件、发布条件和回滚方式是否闭环；
6. 后续通过标准规则测试集、代表性模型、互操作样例和浏览器端到端测试验证实现。

逐项验收设计以 `docs/requirements/opm-requirement-acceptance-matrix.md` 为统一追踪入口；矩阵中的“预期结果”是未来实现的判定口径，不代表当前已有执行证据。

## 17. 风险与待确认项

### 17.1 已确认事实

- 用户要求编辑 OPD 并实时得到文本表达，当前明确首期按照单机版设计；
- 产品需要使用仓库内两份中文资料和 ISO 19450:2024 正文，并以工具制造商符合性为 ISO 目标；
- 中文 OPL 草案与 ISO 19450:2024 存在扩展和差异，不能默认完全等价；
- ISO 文本模态称为 OPL，中文草案文本模态称为 OPT；
- OPM 采用“一个模型、多张相互关联的 OPD”：ISO 配置档以 SD 为 OPD process tree 的唯一根，对象细化形成 OPD object forest，按条件形成的 model view 独立管理；
- 同一语义元素跨 OPD 出现时必须保持稳定身份和一致语义，每张 OPD 均有对应的文本模态段落或章节；
- 当前仓库没有生产应用代码；P0 机器契约、SQLite V1、交互原型、handoff、测试策略和开发执行包已经形成，但原子 `shall` 规则、生产实现和 ISO 测试证据尚未形成。

### 17.2 建议基线

- 首期采用 OPD 编辑、OPL/OPT 文本只读实时生成，避免双事实源；
- 首期采用单用户、单设备、本地存储，不建立用户与权限模型；
- 首期核心建模流程不依赖云端服务；
- 产品采用多配置档方式隔离标准差异；
- 通过阻断性校验的版本由用户主动生成为只读本地基线；
- 模型、OPD、元素、关系、文本模态、版本、校验结果和基线统一作为可演化的业务语义资产管理；
- OPM 基线只作为本体平台的上游语义源，经过明确映射、校验和受控发布后才能成为下游本体资产。

### 17.3 待产品评审确认

1. 自动备份的默认位置、频率和保留数量；
2. 首期是否需要直接编辑 OPL/OPT 文本并反向生成 OPD；
3. 首期需要兼容哪些现有 OPM 工具及其交换格式；
4. 模型是否涉及涉密数据、本地加密或国产化环境要求；
5. 建议性能容量是否符合实际模型规模；
6. 中文 OPL 草案配置档是按当前草案冻结，还是持续跟踪后续正式版本；
7. 产品发布时要求达到部分符合、完全符合，还是同时完成工具制造商符合性的正式第三方验证。
